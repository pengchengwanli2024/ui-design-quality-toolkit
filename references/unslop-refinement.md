# 去模板化 UI 精修：unslop 整合

本文件改编自 **Damir Sokolovsky（[@heydamir](https://x.com/heydamir)）** 的 [unslop](https://github.com/heydamir/unslop)，采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)，许可全文见 [LICENSES/CC-BY-4.0.txt](../LICENSES/CC-BY-4.0.txt)。

改编说明：提炼了上游的界面诊断、产品方向、分层精修和完成后复核方法；将固定风格、尺寸与操作顺序改为按项目证据选择的检查项，与 Oil UI Pro、已有品牌和业务约束结合。未移植上游截图、生成图片或故事视频的脚本与素材。

## 在组合流程中的位置

用户要求去 AI 味、去模板感、精修现有界面，或在设计/改版交付前检查具体视觉问题时使用。Oil UI Pro 继续负责当前任务的设计范围与方向，本文件补充有证据的精修判断。小改动只检查受影响部分；只读评审只给问题和建议。

先看实际页面和对应组件、Token，保留业务功能、内容语义及已确认方向。截图、页面地址或源码无法提供的状态记为未验证；只有一个外部链接时，分析或本地草稿不表示已修改原站。

## 诊断与改动幅度

- 把发现写成“位置与实际现象 → 对阅读或操作的影响 → 源组件/Token → 最小改法 → 验证结果”。颜色、特效或布局的出现本身不是缺陷，需要结合任务、品牌和可用性判断。
- 问题集中在少量局部时，沿用原有配色、字体、布局与素材，只修已定位的问题。没有明显问题时如实说明，不为套用某种审美而重做界面。
- 多处问题共同影响层级和操作时，先沿用 Oil UI Pro 的范围与方向判断，再安排受影响层的修整。已有确认或明确授权直接实施时继续执行，不重新启动确认流程。
- 业务错误、关键操作、可读性与焦点问题先处理；视觉精修不能取代功能、权限或数据完整性检查。

## 从产品本身确定辨识度

把当前用户任务、已确认的产品气质、与产品相关的内容/素材、主要视觉焦点，以及可复用的识别细节连接起来。复用已有的设计说明，不为这一步另写长篇方案。

可用替名检查发现空泛表达：如果只替换产品名，标题、图片和叙述仍适合任何产品，检查是否缺少本产品真实的对象与动作。标准表单、表格和行业通用控件仍应沿用熟悉的模式，不要求每个页面都发明视觉标记或增加插图。

## 分层修整

下列层次来自上游九类精修方法。按根因、改动范围和内容依赖选择顺序；整屏同类问题从共享组件或 Token 一次修复，不复制页面补丁。

| 层次 | 需要确认的实际问题 | 修整与复核 |
| --- | --- | --- |
| 间距 | 同类行高、卡片内边距或对齐不一致，组内/组间关系模糊 | 使用项目现有间距刻度，核对侧栏、长标签、数字列和控件组的对齐；合理的光学微调可以保留 |
| 色彩与表面 | 多处强调竞争、文字角色不清、装饰影响信息层级 | 让语义角色、选中/焦点及业务状态可区分，检查实际背景上的对比度；品牌已确认的渐变、颜色和视觉资产继续按项目使用 |
| 图标 | 图标家族、尺寸、线宽与标签对齐混杂 | 复用项目图标与语义，去掉重复装饰；功能图标、内容中的 Emoji 和用户输入分别判断，保留状态含义与可访问名称 |
| 文案 | 标题空泛、动作不明确、指标没有比较基准、事实缺少来源 | 用真实对象和动作表达；保留必要提示、警告及业务标签，未知指标不改写成看似真实的成绩。演示数据继续明确标识 |
| 字体 | 层级过多、小字拥挤、数字格式与正文节奏不一致 | 使用项目字体与字级，检查中文换行、长内容、数字对齐和目标语言；不统一强制细字重、英文大小写或固定字体 |
| 布局 | 主要任务不突出、官网样式挤占工作台、窄屏只缩小桌面 | 按页面任务分配空间与密度，检查主次操作、表格信息关系、滚动与响应式；改变信息架构或功能入口须属于已授权范围 |
| 组件细节 | 嵌套圆角、表格状态、按钮与输入样式失配 | 从现有组件修正，核对 hover、focus、selected、disabled 及适用的 loading、empty、error；图表类型、颜色和单位服务真实数据含义 |
| 素材 | 图片、样机或装饰与产品无关，图中烘焙的假按钮影响理解 | 优先使用项目可用的产品内容和合规素材，必要文本与操作保留在实际界面；生成图片和付费服务遵守当前授权 |
| 动效 | 无状态意义的循环、过度悬停位移、布局动画导致卡顿 | 动效解释状态或空间变化，指定实际过渡属性并支持减少动态效果偏好；保留项目已确认且可用的叙事动效，不一概删除 |

## 验证与交付

1. 在目标视口重新查看实际页面，并操作受影响路径。逐项核对诊断中的问题，以及修改前已正常的关键行为；颜色、主题、键盘和触控的检查跟随本次影响面。
2. 核对页面的视觉重点是否支持产品任务，同时保留易读、熟悉的业务操作。不能只凭颜色更少、字重更轻或分数更高判断精修成功。
3. Web API、兼容性和性能问题接回 [Web 实现与质量补充](web-quality.md)；项目规范读写接回 [设计参考库转化](design-md-library.md)。没有运行页面时明确标注实际视觉与交互未验证。
4. 交付本次修整、验证证据和未完成项。前后对比沿用当前任务证据，不固定要求九次渲染或限制为三次；只有用户要求分享演示或视频时才安排相应产物，并保留适用的作者与许可说明。
